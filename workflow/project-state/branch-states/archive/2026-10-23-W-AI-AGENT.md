## 4. Architecture

### Repository and persistence

**Now:** migration V006 adds `ticket_assistants` keyed by ticket id with bounded state, rounds and draft, and widens ticket-message authorship to SYSTEM. `TicketAssistant` maps the row; `TicketAssistantRepository` supplies a conflict-safe PENDING insert, WAITING_GUEST compare-and-set and pessimistic locked read. Reset helpers delete assistant rows before messages. No runtime assistant orchestration is built yet.

### Guest message presentation

**Now:** Guest ticket messages share an author-role label helper including `Snoozy · Automated assistant`; ticket conversation entries show the stored last-message body as plain text. Authentication roles and booking conversation presentation are unchanged.

### Agent assistant presentation

**Now:** dispute detail shows the nullable assistant panel above internal notes with state, stale and injection warning copy. Insert into notes copies the complete draft into dirty local notes only for the assigned Agent; polling preserves dirty text and explicit Save retains the existing 4,000-character limit. Agent thread messages share role labels and render SYSTEM text left aligned with preserved line breaks.

### Internal assistant message posting

**Now:** `MessageService.postAssistant` trims and bounds the body, requires an open ticket, and writes SYSTEM-authored messages only to the GUEST channel. It joins the caller transaction and publishes only after commit; the applier will own its audit. No HTTP route exposes this method.

### Agent assistant read projection

**Now:** dispute detail reads its assistant row in a read-only transaction and returns only the seven public fields through a nullable service snapshot and response mapper. Defaults/configured round and stale settings are read independently of runtime feature beans; strict stale age applies only to PENDING rows on open tickets. Queue and Guest/Host contracts remain unchanged.

### Ticket assistant feature definition

**Now:** `service.assistant` defines validated `ClarifyOutput`, bounded configuration, the conditional Guest-only `ticket.clarify` feature, deterministic R4/R4b screens and fixed plain-text report/message rendering. The selected v3 examples prompt includes approved P13 standalone-marker and round guidance; its exact text is mirrored in the tuning kit and pinned by `ClarifyFeatureTest`. R4 canonicalizes the document marker and rejects mixed/contact/subject/UUID overrides. R6 requires a server-loaded ticket UUID and expands only the canonical marker to the fixed support instruction. T10 records a full 21-ticket run and operator KEEP. The runtime now reads immutable snapshots in a read-only transaction, calls the gateway outside transactions, and applies guarded state/message/audit changes in a REQUIRES_NEW transaction. A private bounded asynchronous runner tracks follow-up handoffs through idle waits. Catch-up calls omit only the newest question when an unseen Guest reply precedes it (SD23). `TicketOpenedListener` (after commit; conflict-safe PENDING insert, then submit) and `MessagePostedListener` (plain listener; a Guest reply claims WAITING_GUEST, an Agent post in the GUEST channel stops the row) start and stop turns, each catching every failure. Settings live under `snoozeshare.assistant` in `application.yml` (`SNOOZESHARE_ASSISTANT_*`); the runbook has the diagnosis and rollback notes.

### 4.17 Ticket assistant (`com.snoozeshare.service.assistant`)

**Now:** after a Guest files a ticket, `TicketOpenedListener` (after commit) inserts a `ticket_assistants` row in `PENDING` and submits an `AssistantJob` to the private bounded `AssistantRunner` (daemon threads, abort-on-full queue, never the request thread). The job loads a read-only snapshot (`AssistantContextBuilder`: eight trusted facts, the ticket text, stored question and Guest turns, no Host, Agent, listing or category text), calls the `ticket.clarify` feature on the shared gateway outside any transaction, then `AssistantApplier` applies the result in one `REQUIRES_NEW` transaction under ticket-then-assistant locks: screened questions are posted as SYSTEM messages in the GUEST thread (the fixed support-email line is expanded server-side from the canonical marker), the draft is replaced, and every state change and message gets an `ASSISTANT_STATE` / `ASSISTANT_MESSAGE` audit row with metadata only. `MessagePostedListener` resumes a `WAITING_GUEST` row on a Guest reply (compare-and-set) and stops it on an Agent post in the GUEST channel. A follow-up call runs when a Guest reply arrived during a call; its replay leaves out only the newest question when an unseen reply precedes it (SD23). Rounds are capped (`max-rounds`, default 3), calls are bounded by `max-rounds + 1`, and every failure ends in `UNAVAILABLE`/`STOPPED` with no retry or sweep. The Agent sees the draft only through dispute detail and inserts it into notes by hand. A SYSTEM-authored ticket-thread message means the automated assistant (C174).

## 5. Conventions

- A SYSTEM-authored message in a ticket GUEST thread is the automated assistant; do not use the SYSTEM role for anything else there (C174). Agent text is treated as trusted-for-stop only and never enters the prompt.
- Assistant tests that file tickets must start from `pending()` in `AssistantIntegrationTest` (real listeners run on filing; the helper files with a DISABLED gateway and clears invocations).
- `TicketAssistant` is explicitly keyed by `ticket_id` (approved data model), an exception to the ordinary entity `id` column convention; it is a one-to-one extension of the existing ticket.

## 6. Known Gaps

Accepted limitations are the spec's R12 list (conventions.md): a call lost at a restart leaves the row `PENDING` (shown stale) with no sweep; screens are a floor, not a proof, and drop some harmless text; no re-run after `UNAVAILABLE`; model questions are Guest-influenced; steered prose matching no pattern passes; `flagged` is pattern-based; the feature shares the gateway budget with the other role features and many throwaway Guest accounts can fill the two worker threads and fifty-job queue; drafts and assistant messages persist with the ticket (owner W-SECURITY); with the gateway disabled each ticket still costs a row insert, a job and a delete. The ticket-opened listener inserts its row in a REQUIRES_NEW transaction during the after-commit phase, which can need a second pool connection per filing request under heavy load (code review, not load-tested). Also D118: a 6,000-character draft can exceed the 4,000-character notes limit, so the Agent may need to edit before saving.
