# Requirements

Ordered so that a requirement comes after anything it depends on. "The agent" means a signed-in user whose database role is AGENT and status ACTIVE.

## Functional
| ID | Requirement | Acceptance criterion |
|---|---|---|
| F1 | Every `/api/agent/**` operation takes the acting agent's id from the verified token via `@CurrentUserId`; no path, query or body field can name or change the actor, request bodies reject unknown properties, and a missing actor fails closed with 401 | Given a body containing `agentId` When the operation is called Then 400 `VALIDATION_ERROR` and no service call; every service call in the controller tests receives the id of the token's user; given the filter did not run, the resolver throws and the response is 401 `INVALID_TOKEN` |
| F2 | Every `/api/agent/**` failure, including 404 for an unknown route, 405, 411, 413 and 415, returns `{code, message, requestId}` with the status table in api.md; no stack trace, SQL or class name ever appears | Given each error row in api.md When triggered Then the status and `code` match and the body has exactly those three fields |
| F3 | The agent can list disputes filtered by assignee (ALL, UNASSIGNED, MINE), oldest first, and sees the count of unassigned disputes | Given 3 OPEN unassigned and 1 IN_REVIEW tickets When listing ALL Then 4 items, oldest `createdAt` first, and `unassignedCount` 3; listing MINE returns only the caller's tickets and `unassignedCount` is still 3 |
| F4 | The agent can open one dispute and see the booking, parties, escrow, phase label, requested remedy, assignment and the internal notes | Given a ticket id When GET detail Then `DisputeDetailResponse` with `escrowAmount`, `escrowHeld`, `phaseLabel` and `agentNotes` as the service computes them; `TicketResponse` carries no `agentNotes` |
| F5 | The agent can assign an OPEN ticket to themself, which moves it to IN_REVIEW; two simultaneous assigns produce exactly one winner | Given an OPEN unassigned ticket When assign Then status IN_REVIEW, assigned agent is the caller, one `TICKET_ASSIGNED` audit row; given two threads assigning at once Then one 200, one 409, one audit row |
| F6 | The assigned agent can save internal notes on an IN_REVIEW ticket; `null` and the empty string both store the empty string; notes are never shown to a Guest or Host | Given an IN_REVIEW ticket assigned to the caller When notes are saved Then the detail shows them and one `TICKET_NOTE_SAVED` row exists; 4,000 characters are accepted and 4,001 are not |
| F7 | The assigned agent can resolve an IN_REVIEW ticket with ACCEPT, REJECT or MANUAL, which settles the whole escrow two-sided (C20) and requires a reason. ACCEPT gives RESOLVED_APPROVED, REJECT gives RESOLVED_REJECTED, MANUAL gives RESOLVED_APPROVED when the guest refund is above 0 and RESOLVED_REJECTED when it is 0. A `guestRefund` sent with REJECT, or with ACCEPT on a FULL_REFUND or HOST_PAYOUT ticket, is ignored | Given escrow 100.00 and MANUAL refund 40.00 When resolved Then guest wallet +40.00, host +58.20, platform fee 1.80, status RESOLVED_APPROVED, all in one transaction; given refund 0.00 Then guest +0.00, host +97.00, fee 3.00, RESOLVED_REJECTED; given two threads resolving at once Then one 200, one 409 and each wallet changes once |
| F8 | The agent can read both ticket threads (GUEST, HOST) of any ticket and post to either while the ticket is open | Given an open ticket When posting to HOST Then the message appears in that thread with author role AGENT; given a resolved ticket Then 409; 2,000 characters are accepted and 2,001 are not |
| F9 | The agent can list Guest and Host accounts with status and suspension reason | Given 2 Guests, 1 Host, 1 Agent, the System user When listing Then 3 rows, none an Agent or System |
| F10 | The agent can suspend an ACTIVE Guest or Host or reactivate a SUSPENDED one, with a required reason; suspension cascades as the service defines (cancel pending and not-yet-started confirmed bookings with a 100% refund, deactivate a host's listings) and is all-or-nothing | Given an ACTIVE guest with a confirmed future booking When suspended Then status SUSPENDED, booking cancelled with refund, audit rows written, and the guest's next request returns 403 `PROFILE_INACTIVE`; given a host with two listings and a confirmed booking on one When suspended Then both listings INACTIVE and the booking cancelled and refunded; given a failure mid-cascade Then nothing persists |
| F11 | The agent can search the audit log by text (user name, email, or booking, ticket or user id fragment), a set of action types and an inclusive date range, newest first, in pages of at most 200, and can read the list of action types | Given 450 matching rows When requesting offset 0, 200, 400 with limit 200 Then 200, 200, 50 rows and no overlap; `GET /audit/actions` returns every `AuditAction` name |
| F12 | The agent can list all categories, create, rename, activate or deactivate, and delete a category that no ticket uses | Given a category used by a ticket When delete Then 409 and the category remains |
| F13 | `/agent` redirects to `/agent/disputes`; each tab links to its own route and the current tab is marked; the routes are `/agent/disputes`, `/agent/disputes/{ticketId}`, `/agent/accounts`, `/agent/audit`, `/agent/categories`; the Wallet pill is not shown to agents | Given a signed-in agent When clicking Accounts Then the URL is `/agent/accounts` and the Accounts tab has `aria-current="page"` |
| F14 | The Disputes pages show the queue and detail with the artifact's layout and the desktop's actions, and the Accept, Reject and Manual dialogs require a reason; any error from a resolve call makes the page refetch the detail | Given an unassigned ticket When the agent opens it Then only Assign to me is enabled; after assigning, notes, replies and the three resolution buttons are enabled while the escrow is held |
| F15 | The Accounts, Audit Log and Categories pages show the artifact's layout with the desktop's controls and the states in ui.md | Given the Audit Log page When Apply filters is pressed Then the table reloads from offset 0 with the filter values |
| F16 | The API helpers treat 401 and the 403 codes `PROFILE_INACTIVE`, `PROFILE_NOT_REGISTERED` and `ROLE_MISMATCH` as session failures: the user sees the stable message and is routed by the existing guards, never a raw error | Given a 403 `PROFILE_INACTIVE` from any agent call When it reaches the page Then the "account suspended" message shows and no table renders stale data |

## Non-functional
| ID | Category | Requirement | Acceptance criterion |
|---|---|---|---|
| N1 | Security | No `/api/agent/**` operation runs for an unauthenticated user, a non-agent, an inactive user, a path variant that skips the custom filters, or when security is disabled | Given each case When any agent endpoint is called Then 401, 403 `ROLE_MISMATCH`, 403 `PROFILE_INACTIVE`, the same for the encoded, double-slash and `;` variants, and with `snoozeshare.security.enabled=false` the route is 404 |
| N2 | Money | Money moves only through `TicketService.resolve` and `AccountGovernanceService`; no new ledger write path exists; the frontend performs no money arithmetic or comparison and displays SGD with two decimals | Given the architecture test of N6 Then no class in `api.controller` depends on `LedgerWriter`, `WalletService` or a wallet repository; and a frontend test pins the displayed escrow and refund strings |
| N3 | Audit | Every mutation leaves the audit rows the service writes; the API layer writes none itself | Given each mutating endpoint When it succeeds Then the audit rows of the service exist and no class in `api.controller` depends on `AuditService` (audit reads use `AuditQueryService`) |
| N4 | Privacy | Logs carry only request id, status, code, path and the agent's user id; never a token, reason, note, message body, registration code or the text of a database exception | Given a request with a reason and a note that fails with a forced database error When the log appender is read Then no line contains either string or the SQL parameter values |
| N5 | Performance | Queue, accounts and one audit page respond in time for a data set of 300 tickets, 300 accounts and 2,000 audit rows | The test records the 95th percentile over 20 calls and logs it; it fails the build only above 5 s per call, so slow shared runners do not make it flaky |
| N6 | Maintainability | Controllers are thin: a class in `api.controller` has no field, parameter or return type from `repository`, `domain.model` or `jakarta.persistence`, depends on no repository, `LedgerWriter`, wallet service or `AuditService`, and every `UUID` parameter carries `@PathVariable` or `@CurrentUserId` | The ArchUnit tests of conventions.md pass and fail when each rule is broken in a fixture class |
| N7 | Usability | Dialogs have `role="dialog"`, `aria-modal="true"` and an accessible name, trap focus, close on Escape and Cancel and restore focus to the opener; icon buttons and switches have an `aria-label`; lists are real `<table>` elements with `<th scope="col">` | Vitest asserts each of these on one dialog and one table (E59) |
| N8 | Reliability | Lists refresh by polling (C78): queue 30 s, open dispute detail and threads 10 s, only while the tab is visible; Accounts, Audit Log and Categories refresh on demand and after their own mutations; a response older than the newest request is ignored | Given fake timers and `document.visibilityState` When 31 s pass visible Then one queue refetch; hidden Then none; given two overlapping requests Then only the newer result renders |
