# W-DOMAIN Plan: Port Domain Model + Core Services to Spring Boot

## Context

SnoozeShare is migrating from a JavaFX desktop app to a Spring Boot + Next.js web app. W-INFRA (project skeleton) is done and merged to `development`. W-AUTH (Firebase) is done and merged. W-DOMAIN ports the domain model, repositories, and services — everything except auth and UI.

The existing desktop code lives under `desktop/src/main/java/com/snoozeshare/`. The backend skeleton is at `backend/` on `development` with Spring Boot 3.5.16, Spring Data JPA, Flyway, PostgreSQL, Spring Security, and Firebase Auth.

**Auth integration**: W-AUTH created `users` and `wallets` tables (V002) with Firebase fields. Our domain migration (V003) ALTERs those tables and creates the remaining 11. Services accept explicit `userId`/`role` parameters, so they don't depend on the auth filter.

**Schema convention**: All tables use `id` as the primary key column (established by W-AUTH's V002). All entities use `getId()`.

**Status:** Done (`d96caca`, reconciled in `3eeff49`)

All use `@Id @Column(name = "id") private UUID id` with `getId()`.

- `BookingMessage` — `@Table("booking_messages")`

**Converter:** `AmenitySetConverter` — `AttributeConverter<Set<AmenityType>, String>`

**Non-entity value objects to port later (in T7 with services):** SearchCriteria, AuditCriteria, HostBookingRow, SearchResult, PriceBreakdown, Money, CancellationRefund, Settlement, SettlementBreakdown, DisputeSummary, DisputeDetail, ConversationSummary, BookingConversationSummary, AccountSummary, ListingMetrics, ListingReview, TripFilter, AuditFilter, AuditRecord

**Key pattern change:** Desktop creates new record copies for updates. Spring entities are mutable — load, set fields, let JPA flush. Every service method that does `new Booking(...)` with changed fields must become `booking.setStatus(target)` etc.

## Risks

1. **Record to entity refactoring** is the biggest effort — every service method that creates new record copies must change to entity mutation
2. **LedgerRepository** can't be JPA (WalletTransaction has no table) — use JdbcTemplate
3. **ListingMetricsService** uses raw aggregation SQL — keep as JdbcTemplate
4. **Message reads tables** (markRead/countUnread) need JdbcTemplate for composite-key operations
5. **Wallet concurrency** — desktop was single-threaded; may need `@Version` or pessimistic locking for wallet balance updates
6. **Auth repository overlap** — W-AUTH created `AuthUserRepository` and `WalletRepository` (JdbcTemplate); domain layer creates JPA versions. Decide whether to unify in T5/T7
