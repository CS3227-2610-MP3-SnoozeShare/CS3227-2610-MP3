# Requirements

Ordered so that a requirement comes after anything it depends on.

## Functional
| ID | Requirement | Acceptance criterion |
|---|---|---|
| F1 | The desktop app (`src/`, `build.gradle`, `settings.gradle`, `gradlew`, `gradlew.bat`, `gradle/`, `db/`) lives under `desktop/`, moved with `git mv` so history follows; `config/checkstyle/` stays at the root (SD3). `settings.gradle` keeps `rootProject.name = 'SnoozeShare'` and the shadow jar name is unchanged | Given the test counts (tests, failures, skipped, per class) recorded in the branch state from `desktop/build/test-results` before the move When `./gradlew build` runs in `desktop/` (with xvfb on Linux) after it Then it exits 0 and the post-move counts equal the recorded ones, class for class |
| F2 | `backend/` is a Spring Boot project (Gradle, Java 25, package root `com.snoozeshare`) that builds and tests; `jar { enabled = false }` so only the executable jar is produced | Given Docker is running When `./gradlew build` runs in `backend/` Then it exits 0 and `backend/build/libs/` contains exactly one `.jar` file; without Docker the tests fail with the Testcontainers error and are never skipped |
| F3 | The backend serves `GET /actuator/health` with the database indicator and nothing else | Given the database is reachable When the endpoint is called Then the response is 200 with body exactly `{"status":"UP"}`; Given the database is unreachable Then it is 503 with body exactly `{"status":"DOWN"}` (Spring's default status mapping, stated here so a test asserts it) |
| F4 | `docker-compose.yml` at the repo root defines a `postgres` service, and the backend `dev` profile uses it and runs Flyway on start | Given `docker compose up -d postgres` has finished and is healthy When the backend starts with profile `dev` Then it applies migration `V001__baseline.sql` and `flyway_schema_history` has one successful row for version 001 (asserted by a test against Postgres 17) |
| F5 | The backend allows cross-origin calls from exactly one configured origin, on application endpoints and on the actuator | Given `snoozeshare.cors.allowed-origin=http://localhost:3000` When a preflight `OPTIONS /actuator/health` arrives with `Origin: http://localhost:3000` Then the response allows that origin; with any other origin Then no `Access-Control-Allow-Origin` header is returned; the same holds for a test-only application endpoint |
| F6 | The `prod` profile has no default for the allowed origin or the database settings | Given profile `prod` and any of `SNOOZESHARE_CORS_ALLOWED_ORIGIN`, `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` unset When the application context starts Then startup fails with an exception whose message names a missing variable |
| F7 | `frontend/` is a Next.js 15 (App Router, TypeScript, Tailwind CSS, Shadcn/ui) project whose home page shows the backend status | Given the backend is up When `/` loads Then the page shows `Backend: UP`; Given it is unreachable or non-200 Then it shows `Backend: unreachable`; `npm run lint`, `npm test` (`vitest run`) and `npm run build` exit 0 |
| F8 | CI runs all three components under the existing required check names | Given a pull request When CI completes Then check `checkstyle` has steps `desktop: checkstyle`, `backend: checkstyle` and `frontend: lint`, and check `build` has steps `desktop: build`, `backend: build`, `frontend: test` and `frontend: build`, all passing in the log; both check names are unchanged |
| F9 | A hosted dev environment serves the backend and the frontend from the `development` branch | Given a push to `development` When the deployments finish Then the Railway backend URL returns F3's 200 body and the Vercel frontend URL shows `Backend: UP`; the evidence (both URLs, a UTC timestamp, the `curl` output) is written in `docs/runbooks/dev-environment.md` |
| F10 | Documentation states how to run every component | Given a fresh clone When the reader follows `README.md` Then they reach a running desktop app (on a copy of the mock DB), backend, local Postgres and frontend using only commands in the README, verified by one walkthrough recorded in the branch state; `docs/runbooks/dev-environment.md` lists each account-bound deployment step, its owner (a named team member) and the deployment order |

## Non-functional
| ID | Category | Requirement | Acceptance criterion |
|---|---|---|---|
| N1 | Security | No credential is committed; the actuator exposes `health` only, with no details, no discovery page | Given the files added or changed on the branch under `backend/` (excluding `build/`), `frontend/` (excluding `node_modules/`, `package-lock.json`), `docker-compose.yml`, `.github/` and `docs/runbooks/` When searched case-insensitively for `password`, `secret`, `token`, `apikey` Then every hit is one of: an environment variable name, the documented dev compose credentials `snoozeshare`/`snoozeshare`, or a prose sentence in the runbook; `GET /actuator`, `/actuator/info` and `/actuator/env` return 404 |
| N2 | Reproducibility | Runtime and library versions are pinned; the frontend lockfile is committed; `frontend/.nvmrc` (22) is the only Node source and CI reads it | Given `frontend/.nvmrc`, `frontend/package-lock.json`, `frontend/.npmrc` (`engine-strict=true`), `backend/build.gradle` with exact versions, `docker-compose.yml` (`postgres:17`) Then no dependency uses `latest` or `+`; `package.json` ranges are allowed only because the lockfile pins them; the pinned versions are copied into `README.md` |
| N3 | Performance | The `build` job finishes within 15 minutes on a GitHub-hosted runner with a warm cache | Run time of the first green pull-request run is recorded in the branch state with the run link; if it exceeds 15 minutes the operator decides whether to raise the limit or cut tests (SD4 forbids splitting the job) |
| N4 | Maintainability | Backend Checkstyle reports 0 violations with the shared ruleset (Checkstyle 10.26.1) | `./gradlew checkstyleMain checkstyleTest` in `backend/` exits 0 with no new suppression |
| N5 | Maintainability | Components are isolated: no source file in one of `desktop/`, `backend/`, `frontend/` references a path in another | A grep of each component for `../desktop`, `../backend`, `../frontend` finds nothing; the only `..` reference is `../config/checkstyle/checkstyle.xml` |
