# Requirements

Ordered so that a requirement comes after anything it depends on. "The assistant" is the feature `ticket.clarify` of `api.md`. "Thread" is the ticket's GUEST thread (`messages.channel = 'GUEST'`). A "round" is one assistant message that contains questions. A "call" is one `LlmGateway.run`.

## Functional
| ID | Requirement | Acceptance criterion |
|---|---|---|
| F1 | After a Guest files a ticket, the assistant starts on its own executor and never changes whether, when or how the ticket is filed | Given a Guest files a ticket When the assistant is enabled, disabled, failing, its executor queue is full, or its listener throws Then `fileTicket` returns the same response as before and the ticket is `OPEN` |
| F2 | The first call analyses the ticket and, if key facts are missing, posts one assistant message containing 1 to 3 screened questions in the thread and records round 1 | Given a ticket whose description lacks the dates and the problem When the model returns `enough = false` and two valid questions Then exactly one message by the SYSTEM user is added to the thread, numbering the two questions, and `rounds` is 1 |
| F3 | Each Guest reply posted while the assistant is waiting triggers one new call whose turns are the stored exchange; the call returns either more questions or "enough" | Given state `WAITING_GUEST` When the Guest posts a reply Then exactly one gateway call is made and the state is `PENDING` until it finishes |
| F4 | The assistant never posts more than `max-rounds` question rounds (default 3), compared with the current configured value. After the Guest answers the last round, one final call refreshes the draft, no questions are posted and the closing message is posted | Given `rounds = max-rounds` and a new Guest reply When the call returns questions Then no question message is posted, the draft is refreshed, the closing message is posted and the state is `DONE` |
| F5 | After every successful call the assistant stores a draft report, rendered by the backend into a fixed plain-text template, in its own record (`ticket_assistants.draft`) | Given an ok result When it is applied Then `draft` holds the rendered text of at most 6,000 characters and `draft_updated_at` is the commit time |
| F6 | The Agent sees the assistant's state and draft on the dispute detail, and can insert the draft into the notes box; the system never writes the draft into `tickets.agent_notes` | Given any state When an Agent opens `GET /api/agent/disputes/{ticketId}` Then the response carries `assistant`; and no code path other than `saveNotes` changes `agent_notes` |
| F7 | The Guest sees assistant messages in the thread labelled "Automated assistant"; the Host never sees them | Given an assistant message When the Guest and the Agent read the GUEST thread Then both receive it with `authorRole = SYSTEM` and the UIs label it; the Host's HOST thread, conversation list and unread count never include it |
| F8 | The assistant stops when an Agent posts in the GUEST thread (state `STOPPED`) or the Guest's account is not active; it takes no further step when the ticket is resolved. A call in flight at that moment has no effect | Given state `PENDING` (first call or a reply call) When an Agent posts in the thread before the call returns Then the late result is discarded: no message, no draft change |
| F9 | When the gateway returns a degraded result the assistant ends in state `UNAVAILABLE`, keeps any earlier draft, and posts the closing message if at least one round was asked; when the gateway reports `DISABLED` on the first call, the assistant row is removed | Given the gateway returns `TIMEOUT` on the first call Then state is `UNAVAILABLE`, no message is posted and the ticket is unchanged; given it returns `TIMEOUT` after round 1 Then state is `UNAVAILABLE` and the closing message is posted; given `DISABLED` on the first call Then no `ticket_assistants` row exists afterwards |
| F10 | If the gateway reports `flagged` for the call's input, the assistant posts no further questions, marks the record flagged, posts the closing message if at least one round was asked, and the Agent sees a warning | Given `LlmResult.flagged = true` When the result is applied Then `flagged` is true, the state is `DONE`, no question is posted and the detail response has `assistant.flagged = true` |
| F11 | Every transition into `WAITING_GUEST` (from `PENDING`, except the defensive move), `DONE`, `UNAVAILABLE` or `STOPPED`, and every message the assistant posts, is audited with the exact rows of conventions.md R7, metadata only; the row delete writes none | Given any applied result When it commits Then an `ASSISTANT_STATE` row exists and, if a message was posted, an `ASSISTANT_MESSAGE` row; neither contains message or draft text |

## Non-functional
| ID | Category | Requirement | Acceptance criterion |
|---|---|---|---|
| N1 | Reliability | The assistant adds no work to the request thread of filing a ticket or posting a message beyond handing a job to the executor and one short database write, and no assistant failure reaches that request | Given the gateway stub blocks for 5 seconds When a Guest files a ticket Then the filing response returns in under 1 second; given a listener's database write fails Then the posting request still succeeds |
| N2 | Cost | At most `max-rounds + 1` gateway calls per ticket (4 by default). Derivation: the first call starts at submission; every later call starts from a `WAITING_GUEST` to `PENDING` change, which exists only after a question round; a call that does not end in `WAITING_GUEST` is the last one | Given a conversation run to the cap, at `max-rounds` of 1, 3 and 5 When the calls are counted Then there are at most 2, 4 and 6 |
| N3 | Security | Model text reaches a Guest only as validated, screened questions and a fixed closing sentence, and reaches an Agent only as a draft rendered from the validated record with the `summary` and `hostPoints` screened, as plain text | Given a model reply with a link, an HTML tag, a decision recommendation in `hostPoints`, or a promise question When it is applied Then none of it is shown |
| N4 | Privacy | The prompt contains no user or Host names, email addresses or phone numbers: the trusted context holds only dates, amounts and enum names; the only user-authored text sent is the Guest's own ticket text and replies (sanitized by the gateway); Host- and Agent-authored text (listing title, category label) is never sent | Given a ticket with names and an email in its text, and a Host listing title and an Agent-set category label When the call is built Then the trusted context contains none of the names, the listing title and the category label appear nowhere in the call, and the gateway redacts the email |
| N5 | Resilience | A restart, an outage or a full queue leaves the ticket usable and leaves no state that blocks an Agent | Given the process stops with a call in flight (first call or reply) When an Agent opens the ticket 10 minutes later Then the panel reports "did not finish" and every ticket action works |
| N6 | Testability | All automated tests run with a stubbed gateway; none needs SoCLaaS | Given CI without credentials When the feature's tests run Then they pass |
