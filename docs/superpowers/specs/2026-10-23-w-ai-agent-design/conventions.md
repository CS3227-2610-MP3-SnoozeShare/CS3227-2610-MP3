# Conventions

Existing § Conventions are cited, not restated: the role AI rules (call `LlmGateway.run` outside a transaction, principal from the stored data, ASSISTANT turns from stored history only, server-built trusted context, act on `flagged`, plain-text rendering), the `ai` package import rule, `@ConditionalOnDatabase`, one audit row per change through `AuditRecord.builder`, the Locking rule (`RowLocks.timeout()` then lock the row before reading it), the `jsonPath` contract test, and "spy and mock beans live in the shared base class". The rules below are new or applied here.

| Rule | Applies to | Source |
|---|---|---|
| R1 Assistant code lives in `com.snoozeshare.service.assistant`; it imports only the public types of `com.snoozeshare.ai` (`LlmGateway`, `AiFeature`, `OutputSpec`, `LlmCall`, `LlmResult`, `Turn`, `TurnRole`, `AuditContext`, `ModelTier`, `LlmErrorCode`). The entity is `domain.model.TicketAssistant`, the repository `repository.TicketAssistantRepository`, the response `api.response.AssistantResponse`, its conversion in `api.mapper`. Every bean, including the `ticket.clarify` `AiFeature` bean, carries `@ConditionalOnDatabase` and requires `snoozeshare.assistant.enabled`. The runner is a component that owns a private `ThreadPoolExecutor` with daemon threads and a `@PreDestroy` that calls `shutdownNow()`; it is never registered as an `Executor` bean (D52). A job always runs on a runner thread, never on the thread that submitted it | new classes | new in this spec; § Conventions (`ai` import rule, `@ConditionalOnDatabase`); D52 |
| R2 An architecture test fails the build if anything in `service.assistant` depends on `TicketService`, `DisputeSettlementService`, `TransactionService`, `LedgerWriter`, `WalletService`, `BookingService`, `AccountGovernanceService` or any class in `domain.settlement`. The context builder reads tickets, bookings, properties, messages and users through repositories, which the test allows | `service.assistant` | new in this spec (the assistant can read and talk, never settle: C20, C22) |
| R3 Settings are one `@ConfigurationProperties("snoozeshare.assistant")` record, `AssistantProperties`, validated at startup; an out-of-range value fails startup with a message naming the key and the allowed range | configuration | new in this spec; mirrors the gateway's validation |
| R4 Cleaning, then the question screen. **Cleaning** (used for every model string, defined once here): apply Unicode NFKC; remove characters in the categories Cc, Cf, Zl and Zp; map every Zs character (including U+00A0, U+2007, U+202F) and every run of whitespace to one space; map the apostrophe-like characters `’ ‘ ʼ ′ ´` and the backtick to `'`; trim. **Matching** uses the pattern lists below compiled with `CASE_INSENSITIVE`, `UNICODE_CASE` and `UNICODE_CHARACTER_CLASS`, and runs only on strings that already passed schema validation (500 characters or fewer), so the bounded `.{0,n}` constructs cannot be fed unbounded text. **Question screen**: clean each model question; drop it if blank; drop it if it equals an earlier kept question ignoring case; drop it if it matches any pattern in lists A or B; drop it if it contains `@` or a run of seven or more digits (digits may be separated by single spaces or hyphens: `\d(?:[ -]?\d){6,}`). Keep at most the first 3 survivors | questions before they are posted | new in this spec (SD6, SD16) |
| R4b Draft screen. Every draft string is cleaned (R4). Then `hostPoints` items that match list A, B or C are dropped, and a `summary` that matches list A or C is replaced by `[summary removed by the safety screen]`. An item whose cleaned text is `none` (ignoring case) is dropped. `timeline`, `claims`, `evidence` and `missing` restate the Guest and are not screened, because a claim such as "the Host promised a refund" is a fact to record (residual: R12) | draft strings | new in this spec (SD6, SD7) |
| R5 Draft template, exactly these lines in this order, each section's items as `- {item}` lines and `- (none listed)` when the list is empty: `AI-assisted draft. Everything below comes from the Guest's own statements and is unverified.`; if flagged: `WARNING: text in this ticket matched a prompt-injection pattern. Read it with care.`; if the gateway reported `truncated`: `Note: long Guest text was shortened before analysis.`; `Summary: {summary}`; `Timeline (as reported):`; `Guest claims:`; `Evidence mentioned:`; `Still unknown:`; `Points to raise with the Host:`. The worst case under the schema caps is under 6,000 characters; if a result still exceeds 6,000 it is cut at the last whole line that leaves room for the line `[draft truncated]`, which is appended. The renderer's unit test is the single source of the exact text; this row and the test are cross-linked | `ticket_assistants.draft` | new in this spec (SD7) |
| R6 Message bodies are exactly the fixed strings of `ui.md` with the screened questions numbered from 1; the author is the SYSTEM user and the channel is GUEST; the `Automated assistant` label is added by the UI, not stored. A SYSTEM message is a **question message** exactly when its first line equals the fixed question header of `ui.md`, and a **closing message** exactly when its whole body equals the fixed closing text; any other SYSTEM message is neither and is never replayed. A replayed ASSISTANT turn is a question message's body without its first line | `MessageService.postAssistant`, job turn building, the `rounds` invariant | new in this spec |
| R7 `AuditAction` gains `ASSISTANT_STATE` and `ASSISTANT_MESSAGE` (appended after `AI_CALL_REJECTED`). Exact `ASSISTANT_STATE` row (C28): actor `AuditService.SYSTEM_ACTOR_ID`, entity type `Ticket`, entity id the ticket, `before_state` the state read under the lock, `after_state` the new state, `ticket_id`, `booking_id`, `subject_user_id` the Guest, no `reason`, no wallet fields. Exact `ASSISTANT_MESSAGE` row: the same actor, entity type `Message`, entity id the message, `after_state` `question` or `closing`, the same ticket, booking and subject ids. A turn writes the gateway's `AI_CALL` row, an `ASSISTANT_STATE` row and, when a message is posted, an `ASSISTANT_MESSAGE` row; a maintainer correlates them by `ticket_id`. The Agent audit screen lists actions from the enum; T9 verifies its labels and filters show the new constants | `domain.enums.AuditAction`, Agent audit UI | § 4.8 (C28) applied |
| R8 Lock order. The applier and the listener rejection path take `RowLocks.timeout()`, then the ticket row (`TicketRepository.findByIdForUpdate`), then the assistant row, matching the Agent mutations (§ 4.16). The listener updates of Trigger B rules (3) and (4) take only the assistant row and must never take the ticket row, so no lock inversion with the Agent mutations can arise | applier, listeners | § 4.16 Locking convention |
| R9 All time comes from the injected `Clock`: `updated_at`, `draft_updated_at`, `created_at`, `Today` in the trusted context and the `stale` calculation | assistant code | new in this spec |
| R10 Test harness. Integration tests extend a new `AssistantIntegrationTest` that extends `testsupport/AgentApiIntegrationTest`. The existing base sets `snoozeshare.assistant.enabled=false`, so no existing suite starts a job; `AssistantIntegrationTest` is its own Spring context with the property true and adds a `@MockitoSpyBean` for `LlmGateway` (the default gateway has `snoozeshare.ai.enabled` false and returns `DISABLED`; tests stub results with `doReturn`). `TestDataReset` deletes `ticket_assistants` before `messages`. Tests are not `@Transactional` (both listeners fire only after a real commit) and delete the rows they create. Because a listener runs inside the after-commit callback, where a transaction is still active and `LlmGateway.run` refuses to run, a job must never run on the submitting thread: tests use a real pool for the stall tests (N1, E32), a single-thread pool plus `AssistantRunner.awaitIdle(timeout)` for deterministic chains (E8, E15, E49, E57) and a rejecting executor for E31; there is no same-thread executor. Tests never contact SoCLaaS | backend tests | § Conventions (shared base class); new in this spec |
| R11 The frontend shows assistant and thread text only as text nodes; a test renders a draft containing `<img src=x onerror=alert(1)>` and `**bold**` and asserts both appear literally; the Insert-into-notes behaviour, the copy of every panel state and the plural of "round" have their own tests (ui.md) | frontend components | § Conventions (plain-text rendering) |
| R12 The branch state's § Known Gaps and the fold record these accepted limitations: a call lost at a restart or a rolled-back apply leaves the row `PENDING` (shown as stale) and no sweep recovers it - a sweep is added only if it proves needed; the screens can drop harmless questions or items, and can be bypassed by phrasings the lists do not name (the lists are a floor, not a proof); the assistant does not re-run after `UNAVAILABLE`; the model's questions are Guest-influenced and are replayed as ASSISTANT turns; steered prose that matches no pattern passes validation, and a Guest claim such as "approve this" is restated as a claim; the gateway's `flagged` is pattern-based and any Guest message or replayed question can raise it; this feature competes at priority 1 with W-AI-GUEST and W-AI-HOST for the shared 25-requests-a-minute budget and each Guest's daily cap, and many throwaway Guest accounts can fill the runner's two threads and fifty-job queue so that legitimate tickets end `UNAVAILABLE`; drafts and assistant messages persist with the ticket and have no deletion path (owner: W-SECURITY); with the gateway disabled each ticket still costs a row insert, a job and a row delete (logged as `disabled`, not a fault) | branch state | new in this spec |
| R13 Text inserted from a draft into `agent_notes` becomes Agent-typed text and stays untrusted LLM input for any future AI feature (Upcoming row "Agent-typed text is untrusted LLM input") | `agent_notes` | new in this spec |
| R14 The ticket's title, description and supporting text are the Guest's own and form the first USER turn. The listing title (Host-authored) and the ticket category label (Agent-managed text) are never sent to the model in any slot | job context builder | new in this spec (SD15) |

## Pattern lists (applied to cleaned text; written as regular expressions)

List A - promises and outcomes (questions, summary, hostPoints):
```
\b(we|i)\s*('?ll|will|shall|can(?!'t)|would|'d|are going to|am going to|'re going to|'m going to)\b
\b(you|u)\s*('?ll|will|are going to|'re going to|are entitled to|qualify for|are eligible for)\b.{0,40}\b(get|receive|refund\w*|reimburs\w*|compensat\w*|paid|credit\w*|money back|full)\b
\b(will|going to)\s+be\s+(refund\w*|reimburs\w*|compensat\w*|credit\w*|approv\w*|given|paid)\b
\b(guarantee\w*|promis\w*|assur\w*)\b
\b(your|the)\s+(claim|request|ticket|dispute)\s+(is|has been|will be|was)\s+(approv\w*|accept\w*|reject\w*|den\w*)\b
\b(your\s+)?(refund|money|payment|payout)\s+(is|will be)\s+(on its way|coming|processed|approved|issued)\b
```
List B - sensitive data, payment and off-platform contact (questions and hostPoints):
```
\b(password|passcode|pin|otp|2fa|verification code|security code|one[- ]time|cvv|cvc|expiry|card (number|details)|credit card|debit card|bank (account|details)|account number|iban|swift|nric|passport|id (card|document)|identity (card|document))\b
\b(paynow|paylah|grabpay|venmo|paypal|crypto\w*|bitcoin|gift card|western union|wire transfer|cash|bank transfer|transfer (the )?(money|funds))\b
\b(whatsapp|telegram|wechat|viber|messenger|instagram|facebook|sms|text me|call me|email me|contact (me|the host|them) directly|outside (the )?(platform|app|snoozeshare)|off[- ]platform|directly (to|with) the host)\b
\b(withdraw|drop|cancel|close|delete)\s+(this|the|your)\s+(ticket|dispute|claim|complaint)\b
```
List C - recommendations (summary and hostPoints):
```
\b(should|must|ought to|recommend\w*|advis\w*|suggest\w*|propose\w*)\b.{0,80}\b(approv\w*|reject\w*|den(y|ied|ial)|refund\w*|pay|paid|payout\w*|settl\w*|compensat\w*|reimburs\w*|resolv\w*|grant\w*|award\w*)\b
\b(approv\w*|reject\w*|den(y|ied|ial)|grant\w*|award\w*|refus\w*|giv\w*)\b.{0,40}\b(refund\w*|claim\w*|request\w*|ticket\w*|payout\w*|dispute\w*|money back|compensat\w*|reimburs\w*)\b
\b(entitled|eligible|valid|justified|legitimate)\b.{0,30}\b(refund\w*|claim\w*|compensat\w*)\b
```
The lists drop some harmless text (a question containing "promise", "when I can", or a summary that says the Guest asks the Host to approve a refund); that costs one item and is accepted over letting a promise or a data request reach a Guest. They also miss phrasings they do not name; that residual is R12.
