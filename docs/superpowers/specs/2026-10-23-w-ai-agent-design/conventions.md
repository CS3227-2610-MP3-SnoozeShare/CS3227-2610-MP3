# Conventions

Existing § Conventions are cited, not restated: the role AI rules (call `LlmGateway.run` outside a transaction, principal from the stored data, ASSISTANT turns from stored history only, server-built trusted context, act on `flagged`, plain-text rendering), the `ai` package import rule, `@ConditionalOnDatabase`, one audit row per change through `AuditRecord.builder`, the Locking rule (`RowLocks.timeout()` then lock the row before reading it), the `jsonPath` contract test, and "spy and mock beans live in the shared base class". The rules below are new or applied here.

| Rule | Applies to | Source |
|---|---|---|
| R1 Assistant code lives in `com.snoozeshare.service.assistant`; it imports only the public types of `com.snoozeshare.ai` (`LlmGateway`, `AiFeature`, `OutputSpec`, `LlmCall`, `LlmResult`, `Turn`, `TurnRole`, `AuditContext`, `ModelTier`, `LlmErrorCode`). The entity is `domain.model.TicketAssistant`, the repository `repository.TicketAssistantRepository`, the response `api.response.AssistantResponse`, its conversion in `api.mapper`. | R12 The branch state's § Known Gaps and the fold record these accepted limitations: a call lost at a restart or a rolled-back apply leaves the row `PENDING` (shown as stale) and no sweep recovers it - a sweep is added only if it proves needed; the screens can drop harmless questions or items; the assistant does not re-run after `UNAVAILABLE`; the model's questions are Guest-influenced and are replayed as ASSISTANT turns; steered prose that matches no pattern passes validation, and a Guest claim such as "approve this" is restated as a claim; the gateway's `flagged` is pattern-based and any input (a Host listing title, a replayed question) can raise it; this feature competes at priority 1 with W-AI-GUEST and W-AI-HOST for the shared 25-requests-a-minute budget and each Guest's daily cap; drafts and assistant messages persist with the ticket and have no deletion path (owner: W-SECURITY) | branch state | new in this spec |

## Pattern lists (case-insensitive; written as regular expressions)

List A - promises and outcomes (questions, summary, hostPoints):
```
\b(we|i)\s*(will|['’]ll|shall|can)\b
\byou\s*(will|['’]ll|are going to)\s+(be\s+)?(get|receive|refunded|reimbursed|compensated|paid|credited)\b
\bwill\s+be\s+(refunded|reimbursed|compensated|credited|approved)\b
\b(guarantee|guaranteed|promise|promised|assure|assured)\b
\b(your|the)\s+(claim|request|ticket)\s+(is|has been|will be)\s+(approved|accepted|rejected|denied)\b
```
List B - sensitive data and off-platform contact (questions only):
```
\b(password|passcode|one[- ]time|otp|cvv|card number|credit card|debit card|bank account|iban|nric|passport|paynow|western union|wire transfer|whatsapp|telegram|wechat|outside (the )?(platform|app))\b
```
List C - recommendations (summary and hostPoints only):
```
\b(should|must|ought to|recommend|recommended|advise|advised|suggest|suggested)\b.{0,60}\b(approve|approved|reject|rejected|deny|denied|refund|refunded|pay|paid|settle|settled|compensate|compensated|resolve|resolved)\b
\b(approve|reject|deny|grant|refuse)\b.{0,30}\b(refund|claim|request|ticket|payout|dispute)\b
```
The lists can drop a harmless item (for example a question containing "promise"); that costs one question and is accepted over letting a promise or a data request reach a Guest.
