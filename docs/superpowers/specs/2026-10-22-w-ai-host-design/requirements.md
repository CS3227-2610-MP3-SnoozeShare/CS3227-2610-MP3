# Requirements

## Functional

| ID | Requirement | Acceptance criterion |
|---|---|---|
| F1 | The New and Edit listing forms show an inline `AI Description Assistant` button with a Sparkles-style AI icon beside the Description label without adding a second always-visible editor or changing the existing form field's value on open. | Given either form, when rendered, the existing description field remains in its current card and the assistant trigger is visible on the same label row or its compact wrap; no AI modal is open initially. |
| F2 | The assistant modal provides writing style, target audience, and description length controls with the fixed options in SD2, and copies the current form description into its editable text area on open. | Given a form description value, when the trigger opens the modal, the modal text area equals that value and the selected controls have explicit defaults. |
| F3 | Evaluate analyzes only the current description and returns no generated description. | Given a non-empty current description, when the Host selects Evaluate, the response contains `currentAnalysis`, `generatedDescription: null`, and `generatedAnalysis: null`; no new text is generated. |
| F4 | Generate produces a description using the validated listing context, current description, style, audience, and requested length, including when the current description is empty. | Given any valid draft context and an empty or non-empty current description, when Generate succeeds, the response has `outcome: SUCCESS`, a non-empty generated description, and generated analysis. |
| F5 | Both current and generated analysis contain exactly Clarity, Completeness, and Accuracy rows, each with `PASS` or `IMPROVE` and one concise feedback sentence. | Given a successful Evaluate or Generate response, when the UI renders analysis, each applicable column has the three criteria in that order and no fourth criterion. |
| F6 | Apply copies only a successful generated description into the New/Edit form's controlled description value and closes the modal; it does not call the listing Save endpoint. | Given `outcome: SUCCESS` with generated text, when the Host clicks Apply, the form field contains the generated text, the modal is closed, and no create/update request has been sent. Given `outcome: DEGRADED`, Apply is disabled. |
| F7 | The endpoint authorizes the authenticated Host and prevents access to another Host's persisted listing. | Given a request with a persisted listing id, when the authenticated principal does not own it or it does not exist, the API returns the existing safe not-found contract and sends no LLM request. |
| F8 | The feature sends prompts only through `LlmGateway.run` and returns safe fallback/error results for disabled, throttled, rejected, invalid, unavailable, or audit-failed gateway calls. | Given each gateway failure class, when the endpoint responds, the response has `outcome: DEGRADED`, null analysis/generated fields, and a stable code; no upstream secret/prompt/body is exposed and the UI stays usable with an actionable safe error. |

## Non-functional

| ID | Requirement | Acceptance criterion |
|---|---|---|
| N1 | The backend never sends street address or postal code to the LLM and never logs prompt, response, API key, or host instructions. | Source and integration tests prove address/postal fields are absent from the gateway context and safe-log assertions find no user text or secret. |
| N2 | The feature uses the gateway's JSON validation and plain-text rendering rules. | A malformed, linked, HTML, refusal, or schema-invalid model response is rejected and the UI renders accepted feedback/description as text only. |
| N3 | Controls are disabled and a visible loading indicator is present for the entire Evaluate/Generate request. | During a pending request, dropdowns, radios, text area, action buttons, Apply, and modal close are not actionable; after completion or failure they recover. |
| N4 | The modal preserves the existing Host form layout and is usable at desktop, tablet, and mobile widths. | Existing form tests remain green; desktop/tablet show two columns, and narrow viewports stack the columns without horizontal overflow. |
| N5 | The feature uses the existing gateway's bounded input and token-limited output without silently truncating Host-authored context. | Requests reject fields outside the API limits and reject the serialized untrusted context above the gateway's 8,000-character feature cap before the gateway; generated descriptions are validated against the selected non-overlapping band and the gateway's accepted JSON response. |
| N6 | The gateway call runs outside an active database transaction, uses database-conditional activation, and produces the gateway's metadata-only audit outcome. | Backend tests prove no listing transaction remains open during the LLM call, database-free contexts remain startable, and the gateway receives the authenticated Host id and role. |
| N7 | The feature excludes address/postal fields and relies on the gateway's existing PII sanitization and output validation; it does not claim broader PII detection than the gateway provides. | Address and postal fields are absent from the request context; the gateway sanitizer handles its configured input patterns; accepted output follows the gateway's existing validation. Address/postal detection beyond excluded fields remains a documented limitation. |
