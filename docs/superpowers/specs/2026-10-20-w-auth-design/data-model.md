# Data model and persistence

## User profile

The backend user row is keyed by Firebase UID and contains the application identity, not a password:

| Field | Rule |
|---|---|
| `id` | PostgreSQL UUID primary key, generated by the backend |
| `firebase_uid` | `varchar(128)`, non-null, unique, immutable |
| `email` | `varchar(320)`, non-null verified-token snapshot, lowercase ASCII case-folded for storage; not used as identity key; refreshed from a later verified token only through an explicit future profile-sync operation |
| `role` | `varchar(16)`, non-null, one of `GUEST`, `HOST`, `AGENT`; immutable after registration |
| `display_name` | Nullable `varchar(80)`; trim Unicode whitespace, reject blank after trim and control characters |
| `status` | `varchar(16)`, non-null default `ACTIVE`; W-AUTH recognizes `ACTIVE` only and rejects other values as unavailable |
| `created_at` | `timestamptz`, non-null UTC default `now()` |
| `updated_at` | `timestamptz`, non-null UTC default `now()` |

The existing desktop `SYSTEM` user is not a Firebase-authenticated profile and is outside the W-AUTH registration path; W-DOMAIN owns compatibility with system-wallet behavior.

W-AUTH owns `V002__auth_users_wallets.sql`, an explicit exception to the W-INFRA rule that W-DOMAIN owns every migration after `V001`. It creates `users` and `wallets`. `users.id` and `wallets.id` are PostgreSQL UUID primary keys generated by the backend; `wallets.user_id` is a non-null foreign key to `users.id` with `unique(user_id)`, `currency` is `varchar(3)` default `SGD`, and `balance` is `numeric(19,2)` default `0.00`. Guest/Host registration inserts one wallet; Agent registration inserts none. Existing baseline rows are unchanged. If the migration fails, Flyway leaves the previous schema active and startup fails. W-DOMAIN owns later migrations and must preserve `firebase_uid` uniqueness, role immutability and wallet cardinality.

## Registration codes

Registration codes are server-side reusable secrets, never Firebase claims and never returned to the frontend. The backend reads exactly two values: `SNOOZESHARE_HOST_REGISTRATION_CODE` and `SNOOZESHARE_AGENT_REGISTRATION_CODE`. Missing or blank values fail backend startup with a configuration error. The values are supplied through local environment configuration or the deployed secret store, never committed. Rotation replaces the configured value and takes effect after the backend restarts or reloads configuration. Comparisons are constant-time; submitted and configured values are never logged. Database-backed expiry, one-time use and operator rotation are outside W-AUTH. Five invalid attempts for the same Firebase UID and client IP, or 20 invalid attempts from one client IP across UIDs, within 10 minutes produce `429 REGISTRATION_RATE_LIMITED`; counters are in-memory and process-local and reset on restart.

## Wallet provisioning

Profile creation, role assignment and any required wallet creation run in one database transaction. The database enforces `unique(firebase_uid)` and `unique(wallet.user_id)`. A concurrent unique-constraint loser rolls back, reads the committed profile and returns the same-role idempotent response after validating the required role code; a different-role request returns `409 ROLE_ALREADY_ASSIGNED`. A retry after successful registration returns the existing profile and does not create a second wallet. Display name and email snapshots are not changed by an idempotent retry. A non-`ACTIVE` profile returns `403 PROFILE_INACTIVE` from `/api/auth/me`, registration and role routes; W-DOMAIN owns later lifecycle transitions.
