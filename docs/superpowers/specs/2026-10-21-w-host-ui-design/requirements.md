# Requirements

Ordered so that a requirement comes after anything it depends on.

## Functional

| ID | Requirement | Acceptance criterion |
|---|---|---|
| F1 | The Host UI shall expose `/host`, `/host/listings`, `/host/listings/new`, `/host/listings/:listingId`, `/host/listings/:listingId/edit`, `/host/listings/:listingId/calendar`, `/host/requests`, `/host/messages`, and `/host/wallet`; `/host` shall redirect to `/host/listings`. | Given an authenticated Host, when each route is opened, then the matching artifact screen is rendered and the Host shell remains visible; opening `/host` produces a redirect to `/host/listings`. |
| F2 | An authenticated Host shell shall show the SnoozeShare brand, `Host workspace` pill, wallet balance badge, logout control, and tabs in the order Listings, Requests, Messages, Wallet. | Given an authenticated Host route, when the shell renders, then all five shell elements appear in that order and the active tab matches the current route; guard loading/error/inactive states use the existing W-AUTH responses and do not render the authenticated shell. |
| F3 | The Listings screen shall render the `My listings` heading with its `+ New listing` action on the same row, and listing cards containing warm thumbnail, title, property type, location, nightly rate, booking count, rating, active state and switch, calendar action, and edit action. Cards shall omit the active/inactive pill and present five centered, width-stable groups to the right; calendar and edit actions shall be outlined buttons. | Given the supplied fixture set, when `/host/listings` renders, then four listing cards match the artifact's content hierarchy and control placement, booking/rating values are centered, and toggling availability does not shift adjacent groups; the switch changes only local presentation state. |
| F4 | The Listing detail screen shall render breadcrumbs, listing identity/type/status, address, capacity and timing metrics, description, amenities, review excerpts, and performance metrics with artifact-equivalent grouping. | Given a fixture listing, when its detail route renders, then the page contains all required sections and the `Open Booking Calendar` and `Edit listing` navigation controls. |
| F5 | The New/Edit Listing screen shall render the Basic Details, Location, Capacity & Pricing, and Amenities cards with the artifact's field labels, control grouping, saved values, and Save/Cancel actions. | Given the edit fixture, when `/host/listings/:listingId/edit` renders, then saved amenities are checked, selected statuses display title-case labels, input values use normal weight, and the form layout uses the specified two-column grouping. |
| F6 | The Calendar screen shall render breadcrumbs, month navigation, weekday headings, a complete five-week seven-column calendar grid, legend, Block dates panel, and Current overrides list. | Given a calendar fixture, when `/host/listings/:listingId/calendar` renders, then all 35 dates appear, available/booked/blocked/other-month day states are visually distinguishable, and month navigation updates the visible grid locally. |
| F7 | The Requests screen shall render pending and past request sections with their distinct artifact columns, booking metrics, Approve/Reject controls, and the 3% net-earning explanatory copy. | Given request fixtures, when `/host/requests` renders, then pending rows use the gross/net/rating/action columns and past rows use total/status columns, in artifact order. |
| F8 | The shared Messages and Wallet screens shall use the artifact's Host shell and present the shared list/detail inbox and balance/statement card patterns. | Given the exact message and wallet fixtures in `ui.md`, when the routes render, then list/detail regions, balance summary, statement columns, and empty states match the artifact composition. |
| F9 | Host navigation and presentation controls shall not call a backend endpoint or persist a domain mutation in this slice. | Given any fixture screen, when a control is activated, then links navigate, toggles change only local state, form Save validates and returns to the local detail view, Block/Approve/Reject open and close local confirmation presentation, Send appends only to the local thread, and Top up/Withdraw open local confirmation presentation; no action reports server success or makes a network mutation. |
| F10 | The fixture adapter shall default to `populated` and expose a test-replaceable state provider for `empty`, `loading`, and `error`; all records shall be synthetic and unowned. | Given the same fixture state, when a page is rendered repeatedly, then its text, ordering, values, and visual state are identical; no fixture record is described as belonging to the authenticated Host. |

## Non-functional

| ID | Category | Requirement | Acceptance criterion |
|---|---|---|---|
| N1 | Visual fidelity | The UI shall apply the artifact tokens: canvas `#fdf8f0`, surface `#ffffff`, inset `#f0e8d8`, text `#100604`, muted text `#381a10`, subtle text `#6c4434`, border `#c0a080`, muted border `#d8c4a8`, accent `#98300c`, success `#40680c`, warning `#7e5400`, danger `#980c1c`; type sizes 28/20/15/13/11px; spacing 4/8/12/16/20/24px. | Given a production frontend build at the artifact's reference viewport, when a screenshot comparison is performed, then no component uses the current blue/gray generic palette and all named tokens are present in computed styles. |
| N2 | Role safety | All Host routes shall remain behind the existing `RouteGuard role="HOST"`; fixture data is synthetic and is not presented as private tenant data. | Given a signed-out, loading, inactive, or non-Host profile, when a Host route is opened, then the existing guard response is rendered and Host fixture content is not rendered; given any authenticated Host, bundled synthetic fixtures may render. |
| N3 | Accessibility | Every interactive control shall have an accessible name; form fields shall have labels; status colors shall have text labels; keyboard focus shall be visible. | Given keyboard-only navigation or an accessibility-tree inspection, when each Host page is traversed, then every control is reachable, named, and distinguishable without color alone. |
| N4 | Responsive layout | The Host shell and page cards shall remain usable at 1280×800 desktop size and 768×1024 tablet size without horizontal page overflow. | Given those two viewport sizes, when each route is rendered, then the page has no horizontal overflow and all primary actions remain visible or reachable. |
| N5 | Maintainability | Host page components shall consume fixture data through shared presentation types and shall not import backend, repository, or desktop classes. | Given a source dependency scan, when frontend Host files are checked, then no import crosses into `backend/` or `desktop/`, page-local duplicated fixture records are absent, and the fixture module is the only synthetic data source. |
| N6 | Full-width presentation | Authenticated Host content pages shall span the full available viewport width, rather than being capped at a centered max-width container. | Given any authenticated Host content route, when it renders at desktop or tablet width, then its main page frame occupies the available width with consistent edge padding. |
